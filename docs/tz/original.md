## Разработка AI-агента «Нефтегазовый аналитик» — где нужно использовать Ouroboros

### 1. Общее описание задачи

Необходимо разработать интеллектуального агента в роли «нефтегазового аналитика», способного:
- отвечать на профильные вопросы отрасли,
- прогнозировать цены на нефть с использованием расчётного модуля,
- использовать гибридный поиск: по базе отраслевых отчётов (RAG) и по открытым источникам в интернете,
- отдавать приоритет верифицированной информации из загруженных отчётов.

### 2. Функциональные требования

#### 2.1. Роль и системный промпт агента

Агент должен иметь чётко заданную роль «Старший аналитик нефтегазового рынка» с описанием:
- области экспертизы (Upstream, Midstream, Downstream, ценообразование Brent/WTI/Urals, ОПЕК+, санкционная повестка, спрос/предложение и прочее),
- стиля ответа (структурированный, с цифрами, со ссылками на источники),
- правил поведения при отсутствии данных (явно сообщать о неопределённости, не выдумывать цифры).

#### 2.2. RAG-модуль по отраслевым отчётам

Требования:
- разбиение документов на чанки с сохранением метаданных (название отчёта, дата, страница),
- векторизация с использованием любой современной embedding-модели (OpenAI, BGE, E5, multilingual-e5 и т.п.),
- хранение в векторной БД (Chroma, FAISS, Qdrant, Weaviate — на выбор),
- возврат top-k релевантных фрагментов с обязательным указанием источника в ответе.

#### 2.3. Интернет-поиск

Подключить инструмент веб-поиска (Tavily, SerpAPI, DuckDuckGo, Google Custom Search или аналог) для получения актуальных данных (свежие новости, текущие котировки, заявления регуляторов). Необходимо в рамках веб-запросов фильтровать источники по части желтой прессы.

#### 2.4. Логика приоритизации источников

Агент должен следовать правилу:
1. Сначала искать ответ в базе отчётов аналитических агентств — например, ОПЕК, МЭА, EIA (RAG).
2. Если данных в отчётах достаточно — использовать их как основной источник.
3. Интернет-поиск использовать как дополнение или когда требуется актуальность (новости, текущие цены).
4. В ответе явно маркировать, какая информация откуда получена (например: `[Отчёт OPEC MOMR, март 2025]` vs `[Источник: Reuters, web]`).

#### 2.5. Расчётный модуль прогнозирования цен на нефть

Реализовать отдельный tool/функцию, которую агент вызывает при запросах типа «спрогнозируй цену Brent на 3 месяца», «оцени диапазон цен при сокращении добычи на N млн б/с» и т.п.

Минимальные требования к модулю:
- загрузка исторических данных по ценам (например, через `yfinance`, EIA API или подготовленный CSV),
- реализация минимум двух методов прогноза на выбор: ARIMA/SARIMA, Prophet, экспоненциальное сглаживание, простая регрессия по факторам спроса/предложения, LSTM (опционально),
- возврат прогноза с доверительным интервалом и краткой интерпретацией,
- агент должен уметь самостоятельно решать, когда вызывать этот модуль.

### 3. Технические требования

- Язык: Python 3.10+
- Фреймворк агента: LangChain, LangGraph
- LLM: любая (GPT-4/4o, Claude, GigaChat, YandexGPT, локальная Llama/Qwen) — указать в README, почему выбрана
- Интерфейс: простой UI (Streamlit / Gradio / FastAPI + минимальный фронт)
- Контейнеризация: Dockerfile с возможностью запуска одной командой
- Конфигурация: все ключи и параметры — через `.env` (с примером `.env.example`)

1. Репозиторий на GitHub/GitLab с чистой структурой проекта.
2. Исходный код агента, RAG-пайплайна и расчётного модуля.
3. PDF-отчёты в папке `/data` (или скрипт их загрузки).
4. README с описанием архитектуры, инструкцией по запуску и примерами запросов.
5. Краткий отчёт (1–2 страницы или раздел в README): какие решения приняты и почему, какие ограничения у текущей реализации, что улучшили бы при наличии большего времени.
6. Демонстрационные сценарии — минимум 5 примеров диалогов, показывающих:
   - ответ на основе отчёта,
   - ответ на основе веб-поиска,
   - комбинированный ответ,
   - вызов расчётного модуля с прогнозом цены,
   - корректную обработку запроса вне компетенции агента.
