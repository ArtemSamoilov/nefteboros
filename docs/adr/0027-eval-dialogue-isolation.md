# ADR-0027 — Изоляция диалогов в E2E eval (WSRunner)

- Статус: accepted
- Дата: 2026-05-24
- Связано: ADR-0024 (observability-langfuse), changelog 2026-05-11-eval-rebaseline-v2.3.5, changelog 2026-05-24-observability-eval-robustness

## Контекст

E2E re-baseline v2.3.5 на 100 диалогах (`metrics/runs/...c3c22f6.json`) дал
**43/100 timeout >360s, концентрированных в хвосте** (e2e_0073–0100 почти
сплошь), прогон длился 10ч36м. Предполагался «memory/connection leak в
observability». Диагностика по логам самого прогона (`~/Ouroboros/data/logs/`)
показала другое:

1. **Деградация монотонная, не сбой.** 57 ok / 43 timeout, ноль
   crash/connection-refused в server.log. Время на 10-диалоговый батч росло
   24→27→42→61→112→157 мин. Хвост в ~7× медленнее головы.
2. **Бьёт по всем сценариям, включая безынструментальные** (`out_of_scope`,
   `adversarial` refusal'ы тоже ушли в timeout) → деградация глобальная, не
   tool-specific (не browser/RAG/web).
3. **Контекст растёт до cap.** `task_done` события: одиночные (1-round) задачи
   несут `prompt_tokens` 131k→174k по ходу прогона, упор в `soft_cap=200_000`.
   Multi-round задачи хвоста суммируют 1.3–1.95M токенов.
4. **Источник.** Все 100 WS-диалогов идут в **один серверный чат** (`chat_id=1`
   — server.py `_process_bridge_updates` ставит chat_id по умолчанию 1 для
   UI-сообщений). `ouroboros/context.py::build_recent_sections` инжектит
   `## Recent chat` из **глобального** `data/logs/chat.jsonl` (хвост 1000
   сообщений, без фильтра по диалогу — в отличие от progress/tools, которые
   фильтруются по task_id) в КАЖДУЮ задачу. Каждый диалог дописывает в
   chat.jsonl → следующий наследует историю всех предыдущих → контекст пухнет.

Observability (Langfuse) оправдана: без ключей (условие прогона) langfuse 4.6.1
самоотключается (`auth_check=False`); микробенч 600 циклов span+flush дал
RSS +0.0MB, threads=1 — disabled-клиент инертен и leak'а не создаёт.

**Вывод:** это не observability-leak, а дефект eval-харнесса — диалоги
контаминируют друг друга через общую растущую историю. Baseline v2.3.5 частично
невалиден (хвост умирал от bloat'а, не от качества агента).

## Решение

`WSRunner` (`scripts/eval/eval_e2e.py`) **очищает серверную историю чата перед
каждым диалогом** — `POST /api/chat/clear` (обрезает chat.jsonl + progress.jsonl,
endpoint существует с ADR-0020). Это:

- убирает доминирующий аккумулятор контекста (`Recent chat`);
- не даёт консолидатору сработать (порог 100 сообщений недостижим при очистке
  каждые ~2 сообщения), т.е. вторичный аккумулятор (memory blocks) тоже не
  растёт;
- держит контекст каждого диалога на постоянном базовом уровне + только его
  задача.

Escape hatch `EVAL_CHAT_ISOLATION=0` отключает очистку — для diagnostics и для
будущего genuine multi-turn eval (где история между turn'ами нужна).

## Аргументация

- Каждый e2e-диалог — **независимый тест-кейс**, не turn одной беседы. Лить их в
  один чат — методологически неверно: меряем не per-query качество, а ответы в
  100-turn'ной деградирующей беседе.
- Очистка — минимальное вмешательство через **существующий** контракт
  (`/api/chat/clear`), не трогает агента и продовую семантику.
- Фикс на стороне eval-инструмента, не в коде пайплайнов/скиллов (граница scope
  по договорённости — eval-tool отдельно от продакшн-кода).

## Последствия

- E2E-прогон становится надёжным: контекст плоский → нет хвостового timeout'а →
  осмысленный пересчёт baseline возможен (отдельный воркер).
- Чистый прогон 100 диалогов ≈ 3.5–4ч (базовый контекст ~130k токенов на любой
  analyst-запрос — наследие Ouroboros как self-editing агента; вне scope). Фикс
  даёт **надёжность**, не скорость; параллелизм/облегчение харнесса — отдельная
  задача.
- Multi-turn `follow_up` сценарии при включённой изоляции теряют контекст между
  turn'ами — но WSRunner и так шлёт только последнее user-сообщение (известное
  ограничение), так что регрессии нет; полноценный multi-turn eval включит
  `EVAL_CHAT_ISOLATION=0`.

## Альтернативы (отвергнутые)

- **Distinct chat_id на диалог.** chat.jsonl глобальный, не партиционирован по
  chat_id, а server форсит chat_id=1 для UI-сообщений — не изолирует.
- **Server-side per-session изоляция.** Инвазивно, меняет продовую семантику
  чата ради eval — нарушает «eval тем же путём, что прод».
- **Уменьшить окно `read_jsonl_tail("chat.jsonl", 1000)`.** Не чинит
  накопление, только отодвигает порог.
- **Отключить консолидатор на eval.** Не нужно — очистка chat.jsonl и так не
  даёт ему достичь порога.

## Не в scope (бэклог)

- Рост контекста в длинной **реальной** prod-сессии (та же причина) — легитимная
  отдельная проблема, не блокирует пересчёт E2E.
- Базовые ~130k токенов на analyst-запрос (SYSTEM.md+BIBLE+ARCHITECTURE+…) —
  оптимизация контекста Ouroboros для analyst-домена.
