# ADR-0026 — README sync + docs/modules как карта пайплайнов для оценщика

- **Дата:** 2026-05-11
- **Статус:** Принято
- **Контекст:** Финальный pre-deadline (v2.3.5) sync README + создание карты модулей для оценщика Сбера.
- **Связано:** [ADR-0001 (fork)](0001-fork-ouroboros.md), [ADR-0007 (LLM)](0007-llm-providers.md), [ADR-0014 (LangGraph subgraph)](0014-langgraph-subgraph.md), [ADR-0024 (OU regime)](0024-ou-regime-forecast.md), [ADR-0024 (observability)](0024-observability-langfuse.md).

## Контекст и проблема

К v2.3.5 README расходился с кодом по трём пунктам:

1. **Forecast:** README заявлял «SARIMAX + GBR ensemble», но production-путь после ADR-0024 — `regime-conditioned Ornstein-Uhlenbeck`. SARIMAX/GBR остались только для бэктеста.
2. **Команда индексации:** `python scripts/index_corpus.py` — файла нет; реальный скрипт `scripts/build_index.py`.
3. **Telegram-бот / WIP status:** README показывал `Status: WIP` и общий warning «в разработке», обещал работающий Telegram-бот. На prod-инсталляции Telegram-бот не работает (исходящие к Bot API блокируются RKN), а к финальному web-deploy на Timeweb отношения не имеет. Релиз v2.3.5 — production-ready, `WIP` устарел.

Параллельно — ТЗ §3 требует обоснования выбора LLM, и оценщик-аналитик не имеет «карты пайплайнов» (где какие подграфы, какие метрики, что покрыто eval'ом). Это критически важно для оценки production-readiness в дедлайн-окно.

## Решение

### 1. README

- Снять `Status: WIP` badge → `Release v2.3.5`.
- Заменить заявленный forecast-метод на OU с явной ссылкой на ADR-0024 и кратким обоснованием.
- Заменить команду индексации.
- **Telegram полностью убран из README** — ни секций, ни bullet'ов, ни env-переменных, ни строки в ASCII-tree. Код в `nefteboros/bot/` остаётся как unused subdir; к сдаваемому web-deploy на Timeweb отношения не имеет. Лучше тихое отсутствие, чем громкое «не работает, RKN».
- Добавить раздел **«Выбор LLM»** с тремя провайдерами и обоснованием prod-конфигурации.
- Расширить раздел **«Метрики качества»** — таблица с per-pipeline скриптами, baseline v2.3.5 и плейсхолдер на `docs/eval-results-v2.3.5.md`. Явный дисклеймер про placeholder `eval_citations.py`.
- Добавить раздел **«Архитектура модулей»** со ссылками на `docs/modules/*.md`.

### 2. Каталог `docs/modules/`

Один файл на пайплайн / подграф / самостоятельный модуль:

- `analyst_graph.md` — головной LangGraph.
- `routing.md` — classify_intent + llm_disambiguate.
- `rag.md` — retrieval pipeline.
- `web_search.md` — Brave + уровни + язык.
- `forecast.md` — OU production + статмодели только для бэктеста.
- `citation.md` — D6 validator.
- `consolidator.md` — Ouroboros background.

**Структура каждого файла (обязательная):**

1. Назначение (1-2 строки).
2. Точка входа (file:line).
3. Входы / выходы.
4. Ключевые ADR (ссылки).
5. Метрики — **обязательно** маркер «есть / частично / нет инструментации», с указанием имени span'а и file:line, плюс eval-скрипт и формат вывода.
6. Известные ограничения (если есть).

Правило **«явный сигнал, если метрик нет»** — оценщик сразу видит gap'ы без чтения кода.

### 3. ADR номер 0026

Существуют коллизии: два `0016-*.md` и два `0024-*.md`. Дополнительно: `nefteboros/graphs/analyst_graph.py:4` уже ссылается на «ADR-0025 (observability — `@observe` через wrap при `add_node`)», хотя файла такого нет (опечатка, должна была быть ссылка на `0024-observability-langfuse.md`). Чтобы рецензент не открывал `ADR-0025`, ожидая observability, и не натыкался на modules-structure — **этот ADR берёт номер 0026**. Renaming legacy ADR и правка опечатки в коде — отдельные задачи (см. backlog в changelog).

## Почему так

- **README как лицо проекта.** Оценщик из Сбера открывает README первым делом. Лживые claims (SARIMAX, несуществующий скрипт, WIP status на production-ready релизе, рабочий Telegram-бот) подрывают доверие сильнее, чем технические недочёты.
- **Telegram удалён полностью, а не «помечен как отключённый».** К сдаваемому решению Telegram отношения не имеет; web-deploy на Timeweb — это веб-интерфейс. Упоминание «реализован, но не работает» — шум, который заставляет рецензента читать про RKN, прокси и compliance вместо того, чтобы оценивать аналитический контент.
- **docs/modules как «карта для рецензента».** Без неё нужно читать `analyst_graph.py`, `plugin.py`, `nefteboros/observability/` параллельно, чтобы собрать картину. С ней — один файл на пайплайн, один взгляд на «что измеряется, что нет».
- **Маркер «нет инструментации»** — это не недостаток, это явный сигнал. Better honest gap than hidden gap. Consolidator действительно не покрыт eval'ом; pretend в README этого не починит, но запутает рецензента.
- **`eval_citations.py` дисклеймер.** Baseline `cite=0.181` без указания, что offline-валидатор — заглушка, вводит в заблуждение: можно подумать, что валидатор работает плохо, тогда как он не запущен.

## Альтернативы рассмотренные

- **Inline в `architecture.md`** (без выделенного `docs/modules/`). Отвергнут: `architecture.md` — это Mermaid-схема плюс общая картина; per-pipeline детали с метриками туда не помещаются без потери читаемости.
- **Wiki / отдельный сайт документации.** Отвергнут: лишний инфраструктурный шаг до дедлайна; маркдаун в репо проще для оценщика (один git clone).
- **Переименование коллизионных ADR (0016, 0024)** в этом PR. Отвергнут: ломает ссылки в коде (`api.py:5`, `analyst_graph.py:4`, changelog'ах). Отдельная задача с trace всех ссылающихся файлов.
- **Оставить Telegram-секцию в README с честной пометкой «не работает в prod».** Отвергнут: рецензент тратит время на чтение про сетевые ограничения, не на оценку доменной логики. Удалить полностью — экономнее и честнее («не сдаём Telegram в этом релизе» лучше «сдаём, но он не работает»).

## Слабые места

1. **Плейсхолдер-ссылка** на `docs/eval-results-v2.3.5.md` — этот файл создаёт параллельная сессия. До её мерджа в README будет битая ссылка.
2. **ADR-0026 не исправляет коллизии 0016/0024** — оставляет долг.
3. **Маркер «нет инструментации»** в module-docs опирается на статический grep по `@observe` / `traced_tool` / `log_llm_usage`. Если кто-то добавит другой механизм трейсинга, ярлык устареет — должен обновляться вручную.
4. **Структура `docs/modules/` не сцеплена с CI**. Можно добавить module-doc на новый пайплайн и забыть. На будущее: CI-чек «каждому новому файлу в `nefteboros/graphs/nodes/` соответствует module-doc» — отложен в backlog v2.6.
5. **Telegram-код остаётся в `nefteboros/bot/`** без упоминания в README. Если другой разработчик откроет директорию, увидит «непонятную фичу». Документация на сам код есть в SKILL.md/docstrings — но связать README и `nefteboros/bot/` некому. Считаем приемлемым: rare path, и удалять рабочий код за день до сдачи — лишний риск.
