## Задача

Превратить 25 Markdown-файлов из `data/markdown/` (выход PR A) в **тегированные чанки**, готовые для эмбеддинга в PR C: heading-aware splitting + табличная спецлогика + 3-уровневая система тегов (source / section / topic).

## Что сделано

### Код

- `nefteboros/rag/schema.py` — Pydantic-модели:
  - `Chunk` (id, text, source/section/topic поля, page_start/end, has_table, is_table_only)
  - `TopicTags` (5 осей закрытого словаря)
  - `chroma_metadata()` — flat-сериализация для будущего PR C
- `nefteboros/rag/topic_vocabulary.py` — закрытый словарь **5 осей × 22 значения**:
  - `energy`: oil / gas / lng / oil_products
  - `market_aspect`: supply / demand / prices / inventories / trade / infrastructure
  - `geopolitics`: sanctions / conflicts / energy_security
  - `finance`: corporate_finance / government_finance / strategy / forecast
  - `region`: russia / europe / us / middle_east / asia
  - Каждое значение — с человекочитаемым описанием для LLM-промпта
  - Helpers: `is_valid()`, `filter_valid()` для защиты от LLM-галлюцинаций тегов
- `nefteboros/rag/chunker.py` — heading-aware splitter:
  - `parse_markdown()` — MD → AST из MdBlock (heading / paragraph / table) с pageнумерами
  - `split_into_chunkspecs()` — heading-aware с target=3000 / max=4000 токенов
  - `_split_table_block()` — спецлогика для больших таблиц с **fallback в плоский режим** на широких таблицах от Marker (см. калибровку в ADR-0011)
  - `_merge_tiny()` — мерджит чанки <200 токенов с соседями (кроме table_only)
  - `chunk_md_file()`, `iter_chunks_for_corpus()` — entry points
- `nefteboros/rag/tagger.py` — LLM-based topic-classification:
  - `tag_chunks_async()` — async с semaphore concurrency=20, через **kimi-k2p6** (HydraGPT)
  - System-prompt с полным словарём + описаниями
  - 3 retry с экспоненциальной задержкой; на provals — пустые tags + log warning
  - Парсер ответа толерантен к code-block обёртке
  - Все теги валидируются через `filter_valid()` против словаря
- `scripts/chunk_corpus.py` — идемпотентный CLI:
  - `--only <substr>[,...]` фильтр source_id
  - `--force` перезаписать существующие JSONL
  - `--no-tag` только chunking (для отладки/быстрого smoke)
  - `--model` другая модель LLM (default kimi-k2p6)
  - `--concurrency` размер пула (default 20)

## Калибровка и решения

### Marker-артефакт: `<br>` в широких таблицах

EI Statistical Review (74-е изд.) содержит исторические серии с десятками колонок. Marker сворачивает их в одну MD-row с многострочными ячейками через `<br>` — например `| Mexico<br>US | 7.92<br>92.43 | ... |`. Прямой split по `\n` даёт чанки 10K+ токенов (сверх BGE-M3 limit 8192).

**Решение:** в `_split_table_block` добавлены 4 триггера для перехода в **плоский режим** (разворачиваем `<br>` → `\n`, режем как plain text, теряем табличную структуру но сохраняем семантику):
1. ≤2 строк (giant single-row)
2. Любая row с tokens > max_tokens
3. Header занимает >40% max_tokens
4. Общий объём >4× max_tokens с >50 `<br>`

После фикса: 0% чанков превышают BGE-M3 limit (было 16%).

### Размер чанков — крупный (Артём)

Target 3000 / max 4000 токенов — оптимизировано под Kimi 2.6 (256k context), мелкие 500-токеновые чанки создают шум при retrieval. Артём прямо обозначил «не мельчить под Kimi».

### Tagger через kimi-k2p6 (Артём)

Изначально планировал glm-5 (быстрее/дешевле), но Артём попросил kimi для лучшего качества классификации (токены через HydraGPT неограничены). По факту: 802 чанка / ~18 минут / concurrency=20 (HydraGPT режет параллелизм rate-лимитом).
